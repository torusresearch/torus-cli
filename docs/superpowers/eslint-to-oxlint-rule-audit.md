# ESLint to Vite+ / Oxlint rule audit

Status: **partial implementation**. The old ESLint CLI and config packages are removed. Native Oxlint checks run by default. Vize and Tailwind checks are optional and pass one real fixture each. The remaining rules below are not proven equal; do not claim full parity.

## Scope and method

This audit compares the evaluated flat-config rule keys from the five published `@toruslabs/eslint-config-*` packages against the registered rules in the worktree's Oxlint **1.88.0**, used by Vite+ **1.3.0**. The comparison includes inherited recommended configs, not only the rules written in each `index.js`. Disabled rules are excluded; rules from file-specific configs are included. Registration proves that a rule exists, **not** that its options, severity, parser, fix, or behavior match ESLint. Rules from `@typescript-eslint` and `react-hooks` use Oxlint's `typescript/` and `react/` namespaces. The rule lists below are a migration map, not an approved preset.

Existing shared config: `lintPreset()` enables only the TypeScript plugin and a custom `no-unused-vars`; `formatPreset()` sets print width 150, double quotes, semicolons, ES5 trailing commas, and import sorting. It does **not** enable native React, JSX a11y, Node, Promise, Vitest, Vue, or import plugins. `sortImports: true` is an Oxfmt operation, not evidence that ESLint `simple-import-sort` groups or export sorting match.

## Package map

### JavaScript (`eslint-config-javascript/index.js`)

- Direct native candidates: ESLint recommended (except `no-dupe-args`, `no-octal`), `import/extensions`, supported import/recommended rules, Promise recommended, Vitest recommended, `no-console`.
- Formatting candidates: `prettier/prettier`, `quotes`, `semi`, `linebreak-style`, and import order move to Oxfmt. `simple-import-sort/exports` has no verified equivalent.
- Gap: `import/no-unresolved` is not registered natively. A JS plugin or consumer-level resolver/type check needs a proof fixture.
- Explicit exceptions: `import/prefer-default-export`, `no-dupe-class-members`, and `no-useless-constructor` are disabled; preserve intent when enabling a broad rule group.

### TypeScript (`eslint-config-typescript/index.js`)

- Inherits the JavaScript, Promise, import, Vitest, and format items. Native TypeScript candidates include `no-array-constructor` only via a different core rule, `no-unused-expressions`, `no-unused-vars`, `no-dupe-class-members`, and `no-useless-constructor` via core ESLint rule names where semantics permit; they do **not** exist with the `typescript/` prefix in Oxlint 1.88.0.
- Explicit uncovered rules: `@typescript-eslint/naming-convention` (typeLike formats), `@typescript-eslint/member-ordering`, `tsdoc/syntax` warning, and `import/no-extraneous-dependencies` with allowances for tests, helpers, Storybook, and config files. No native equivalents were registered.
- Resolution gap: `import/no-unresolved` plus the configured TypeScript import resolver needs separate checks against `tsconfig.json` paths and package exports. A type check is not an automatic substitute for the ESLint rule.
- Unused-variable behavior: the current rule uses `args: "after-used"` and `argsIgnorePattern: "_"`; the present `lintPreset()` uses `args: "none"`, more ignore patterns, and `ignoreRestSiblings: true`. These are not equal. Use sample cases before selecting shared or per-package options.
- `@typescript-eslint/no-unused-expressions` is disabled for JSON files. Confirm JSON handling before replacing this override. Type-aware rules must remain opt-in until a TypeScript project baseline passes.

### React (`eslint-config-react/index.js`)

- Inherits TypeScript rules and adds recommended React, React Hooks, and JSX accessibility rules. Oxlint registers many `react/` and `jsx_a11y/` counterparts, including `react/rules-of-hooks` and `react/exhaustive-deps`; enable both native plugins and compare recommended severities on TSX fixtures.
- Registered-rule gaps from inherited React recommendations: `react-hooks/config`, `react-hooks/gating`, `react/jsx-uses-vars`, `react/no-deprecated`, and `react/prop-types`. A matching name for another hook rule does not prove compiler-rule parity. Check whether TSX analysis already accounts for JSX component uses before omitting `jsx-uses-vars`.
- `@poupe/eslint-plugin-tailwindcss` recommended adds 15 active rules: `no-duplicate-imports`, `no-duplicate-reference`, `no-empty-blocks`, `no-important`, `no-invalid-at-rules`, `no-invalid-named-grid-areas`, `no-invalid-properties`, `no-arbitrary-value-overuse`, `no-conflicting-utilities`, `prefer-theme-tokens`, `require-reference-in-vue`, `use-baseline`, `valid-apply-directive`, `valid-modifier-syntax`, `valid-theme-function`. None is registered in Oxlint's built-in rule inventory. **Selected replacement:** [`oxlint-tailwindcss`](https://github.com/sergioazoc/oxlint-tailwindcss) for JS/TS/TSX Tailwind class checks. Do not assume its 27 rules replace all 15 `@poupe` rules; test each required behavior and keep a separate check for CSS and Vue-template gaps.
- Explicit overrides also disable `react/require-default-props` and `no-restricted-exports`; keep these decisions visible.

### Vue (`eslint-config-vue/index.js`)

- Inherits TypeScript rules and adds `eslint-plugin-vue` flat/recommended, Vue TypeScript config, Vue i18n flat/recommended, and the 15 Tailwind rules above. The evaluated config enables many Vue **template** rules and 12 Vue i18n rules.
- Oxlint 1.88.0 registers 46 `vue/` rules, mostly script / `<script setup>` checks such as `no-dupe-keys`, `no-side-effects-in-computed-properties`, `valid-define-props`, and `valid-define-emits`. **Its native Vue plugin does not replace template validation.** Do not infer `.vue` template coverage from successful script linting.
- Template/parser rules with no registered native counterpart include `vue/no-parsing-error`, `vue/no-duplicate-attributes`, `vue/no-mutating-props`, `vue/no-unused-vars`, `vue/no-use-v-if-with-v-for`, `vue/require-v-for-key`, `vue/valid-v-if`, `vue/valid-v-for`, `vue/valid-v-model`, `vue/valid-v-on`, `vue/valid-v-slot`, and the remaining `vue/valid-*` directive family. Style/layout gaps include `vue/html-indent`, `vue/html-quotes`, `vue/attributes-order`, `vue/block-order`, `vue/v-on-style`, and other template rules. Formatting can cover layout only; it cannot replace semantic template checks.
- All 12 enabled i18n rules lack a registered native equivalent: `no-deprecated-i18n-component`, `no-deprecated-i18n-place-attr`, `no-deprecated-i18n-places-prop`, `no-deprecated-modulo-syntax`, `no-deprecated-tc`, `no-deprecated-v-t`, `no-html-messages`, `no-i18n-t-path-prop`, `no-missing-keys`, `no-raw-text`, `no-v-html`, `valid-message-syntax`. Vize covers only some use cases; mark remaining checks uncovered until a non-ESLint alternative passes fixtures.
- The Vue config expressly disables `vue/html-self-closing`, `vue/max-attributes-per-line`, and `vue/multi-word-component-names`. Its unused-variable options differ from both the TypeScript legacy config and the current Vite+ preset.
- **Chosen Vue candidate:** use [Vize's Oxlint bridge](https://vizejs.dev/guide/oxlint/) for full-file Vue rules, with a native Vize task for template-only SFCs. Vize lists candidates such as `vue/no-unused-vars`, `vue/no-duplicate-attributes`, `vue/require-v-for-key`, and `vue/valid-v-model`. This is not the same as Oxlint's built-in script-only `vue` plugin. Compare every required ESLint rule and its options before retiring the Vue ESLint package. Keep separate checks for i18n and Tailwind gaps until proven otherwise.

### Node (`eslint-config-node/index.js`)

- Inherits TypeScript rules and adds `eslint-plugin-n` flat/recommended-script and `eslint-plugin-security` recommended.
- Native `node` plugin has 11 registered rules, but lacks these active `n/` rules: `no-deprecated-api`, `no-extraneous-import`, `no-extraneous-require`, `no-missing-require`, `no-process-exit`, `no-unpublished-bin`, `no-unpublished-import`, `no-unpublished-require`, `no-unsupported-features/es-builtins`, `no-unsupported-features/es-syntax`, `no-unsupported-features/node-builtins`, `process-exit-as-throw`, `hashbang`. In particular, the explicit `n/no-unsupported-features/es-syntax` Node >=20 check has no native match.
- No `security/` rules are registered natively. The inherited security recommended config enables: `detect-buffer-noassert`, `detect-child-process`, `detect-disable-mustache-escape`, `detect-eval-with-expression`, `detect-new-buffer`, `detect-no-csrf-before-method-override`, `detect-non-literal-fs-filename`, `detect-non-literal-regexp`, `detect-non-literal-require`, `detect-object-injection`, `detect-possible-timing-attacks`, `detect-pseudoRandomBytes`, `detect-unsafe-regex`, `detect-bidi-characters`.
- Explicit `n/no-missing-import` is disabled; do not re-enable it by applying a group without checking overrides. A code scanner is not a demonstrated substitute for ESLint security rules.

## Options for approval

**Chosen direction: no ESLint CLI or legacy config packages.** Use native Oxlint and Oxfmt for shared checks, Vize for Vue templates (including a native task for template-only SFCs), and `oxlint-tailwindcss` for consumer-owned Tailwind v4 JS/TS/TSX class checks. Allow ESLint-origin rule plugins through Oxlint `jsPlugins` only after fixture tests prove them. Document each rule that remains uncovered; do not describe approximate checks as equal. Do not run a separate ESLint check or retain legacy config packages.

**Alternative considered: native Oxlint only.** Fewer dependencies, but it drops known Vue i18n, Tailwind, Node security, and TS/import policies. This does not meet the user's rule-migration goal.

**Alternative considered: ESLint alongside Oxlint.** This could retain exact legacy behavior, but the user rejected keeping the ESLint CLI and config packages.

## Required proof before config changes or deletion

1. Build a small fixture for each package and collect **effective** ESLint diagnostics and Oxlint diagnostics, not only registered rule names. Include `.js`, `.ts`, `.tsx`, `.vue` template + `<script setup lang="ts">`, a locale file, Node ESM, imports, and Tailwind usage.
2. Test each legacy override: unused args, import extensions and resolver, default exports, disabled Vue style rules, React Hooks, Node >=20 syntax, and security findings. Check recommended severities and file globs.
3. Verify `vp check`, `vp lint`, `vp fmt --check`, and Vize's native task on actual fixtures. Do not add an ESLint CLI step. Keep consumer-specific Tailwind dependencies and CSS paths in each consumer.
4. Remove the five published legacy ESLint config packages and the ESLint CLI as part of the agreed migration; confirm package/export/Changesets consumers first. Run separate non-ESLint tests or document uncovered rules instead of claiming parity. No deletion or release is approved by this audit alone.

## Alternative tools and rule paths (research; not configured)

The installed baseline remains Vite+ 1.3.0 / Oxlint 1.88.0. The sources below describe available tools; they do not prove that this repository can run every rule through `vp lint`. Keep the consumer's own Tailwind version and CSS entry point in its repository.

### Vue templates, Vue i18n, and Vue TypeScript

- **Preferred Vue candidate, per user direction:** [`oxlint-plugin-vize`](https://vizejs.dev/guide/oxlint/) makes Vize's Vue-aware diagnostics available as Oxlint JS plugin rules. Vize's [rule catalog](https://vizejs.dev/rules/all/index.html) lists matching names for many legacy template checks, including `vue/no-duplicate-attributes`, `vue/no-mutating-props`, `vue/no-unused-vars`, `vue/no-use-v-if-with-v-for`, `vue/require-v-for-key`, `vue/valid-v-if`, `vue/valid-v-model`, `vue/valid-v-on`, and `vue/html-quotes`. In Oxlint, these rules have the `vize/vue/*` prefix; compare actual findings, severity, and options with ESLint, not names alone. `vue/no-bare-strings-in-template` is a candidate for some `@intlify/vue-i18n/no-raw-text` use cases, not an exact replacement. `ecosystem/vue-i18n-no-missing-key` covers **local SFC** messages, not all external locale files or the other i18n rules. [Vize ecosystem rules](https://vizejs.dev/rules/ecosystem/index.html).
- **Configure the command actually used:** `vp lint` and `vp check` read the `lint` block in `vite.config.ts`, **not** `.oxlintrc.json`. Vize provides `createVizeLintConfig()` / `defineVizeLintConfig()` to include `jsPlugins` and keep `vize/*` rules and `settings.vize.preset` aligned. `preset: "incremental"` selects only listed rules; `"happy-path"` is its baseline. When composing with the existing preset, preserve all wanted native plugins: setting `plugins` replaces Oxlint's default set. Test that `vp lint` emits a real `vize/vue/*` diagnostic and fails on a bad fixture. [Vize Oxlint guide](https://vizejs.dev/guide/oxlint/), [Oxlint plugin config](https://oxc.rs/docs/guide/usage/linter/js-plugins.html).
- **Template-only and diagnostic location:** Vize warns that direct `vp lint` / `vp check` can skip SFCs without a script block. Its native task via `@vizejs/vite-plugin/vite-plus` and `vize` runs through `vp run lint` (or `vp run vize:lint` if `lint` is already a package script); `oxlint-vize` is a separate wrapper for direct Oxlint. Vize warns that JS-plugin diagnostics can point to the wrong location inside an SFC and that JSON positions are best-effort. Test a template-only SFC and CI's machine-readable output before claiming coverage. [Vize Oxlint guide](https://vizejs.dev/guide/oxlint/).
- **Remaining i18n/type gap:** Vize documents only a local-message missing-key check and a template raw-text check among the old i18n policies. It does not establish parity for `valid-message-syntax`, `no-html-messages`, deprecation checks, or external locale-file resolution. Find a non-ESLint check for each needed rule or mark it uncovered; do not silently remove it. Vize's type-aware exports are experimental; use `vue-tsc --noEmit` for a verified SFC type check unless its native type-check path passes a consumer fixture. [Vize Oxlint guide](https://vizejs.dev/guide/oxlint/).

### Tailwind

- **Selected tool:** use [`oxlint-tailwindcss`](https://github.com/sergioazoc/oxlint-tailwindcss) through Oxlint `jsPlugins` for Tailwind class checks. It requires Tailwind CSS v4.1.15+ and a consumer-owned `settings.tailwindcss.entryPoint` that points to the CSS file with `@import "tailwindcss"`. Keep that path and the dependency opt-in at the consumer: this preset package has no shared Tailwind stylesheet or Tailwind runtime. For `vp lint` / `vp check`, put the plugin and settings in the `lint` block of `vite.config.ts`, not only in `.oxlintrc.json`. Verify a misspelled class fails the Vite+ command. [Setup guide](https://oxlint-tailwindcss.pages.dev/setup), [Vize command/config distinction](https://vizejs.dev/guide/oxlint/).
- **Coverage boundary:** the tool reads classes in JS/TS/JSX/TSX, including supported class attributes and helpers. Oxlint passes only script blocks from `.vue`; it does not pass Vue template classes or CSS files to this plugin. Its rules are not a one-for-one replacement for `@poupe`'s 15 active Tailwind rules, especially CSS directives, properties, and Vue `require-reference-in-vue`. Test a non-ESLint CSS/Vue check for required behaviors or list each lost rule; do not claim parity because JS/TSX fixtures pass. [Tool README](https://github.com/sergioazoc/oxlint-tailwindcss), [current ESLint plugin](https://github.com/poupe-ui/eslint-plugin-tailwindcss).
- **Rule candidates to test:** compare `tailwindcss/no-conflicting-classes` against `@poupe`'s `no-conflicting-utilities`, `tailwindcss/prefer-theme-tokens` against the same-name rule, and the tool's `no-unknown-classes`, `no-duplicate-classes`, and `no-deprecated-classes` against the policy consumers need. Matching names or similar findings do not prove equal rules. Test the real Tailwind design system, plugins, class helpers, and autofix output in a consumer fixture. [Tool rule set](https://github.com/sergioazoc/oxlint-tailwindcss).
- **Sorting only:** [Oxfmt `sortTailwindcss`](https://oxc.rs/docs/guide/usage/formatter/sorting.html) sorts class names with a consumer-owned stylesheet and helper list. It cannot replace semantic Tailwind checks such as invalid modifiers or directives.

### Other missing rules

- **ESLint core:** [`oxlint-plugin-eslint`](https://oxc.rs/blog/2026-03-11-oxlint-js-plugins-alpha.html) supplies the unregistered `no-dupe-args` / `no-octal` under its `eslint-js/` namespace. First verify actual ESLint-vs-Oxlint diagnostics and whether the parser itself catches the syntax; avoid a duplicate check.
- **Import resolution:** Oxlint [does not plan native `import/no-unresolved`](https://github.com/oxc-project/oxc/issues/1117). Use TypeScript `tsc --noEmit` or Vite+ build for their respective projects, and test an aliased `eslint-plugin-import` JS rule in Oxlint if exact resolver behavior matters. `import/no-extraneous-dependencies` is a package-manifest policy rule; test that aliased JS rule in Oxlint or mark the policy uncovered. Neither type checking nor bundling alone enforces its dev-dependency exceptions. An [Oxlint JS plugin alias](https://oxc.rs/docs/guide/usage/linter/js-plugins.html) is possible, but plugin behavior and TypeScript resolver settings require a fixture.
- **TypeScript conventions:** test `@typescript-eslint/eslint-plugin` through an aliased Oxlint JS plugin for `naming-convention` and `member-ordering`; mark the rule uncovered if it does not work or lacks needed parser features. Test native ESLint-core counterparts separately for `no-unused-vars`, `no-unused-expressions`, `no-dupe-class-members`, and `no-useless-constructor`. [`eslint-plugin-tsdoc`'s `tsdoc/syntax`](https://github.com/oxc-project/oxc/discussions/14862) has a community compatibility report; confirm against the installed `0.5.2` before adopting. Oxlint JS plugins do not support type-aware rules; use Oxlint's **native** type-aware mode only after a passing project check. [JS plugin limits](https://oxc.rs/docs/guide/usage/linter/js-plugins.html).
- **Node runtime and security:** try aliased `eslint-plugin-n` JS rules only for missing `n/*` checks; mark Node-version compatibility uncovered until fixtures prove the alias works. A [community test](https://github.com/oxc-project/oxc/discussions/14862) reports several `eslint-plugin-n` rules working in an older Oxlint, but does not prove our Node >=20 option. Try `eslint-plugin-security` as an Oxlint JS plugin for its 14 active rules and compare findings; otherwise mark the affected security rules uncovered. CodeQL/Semgrep can add scanner coverage, but they are not rule-by-rule replacements. [JS plugin docs](https://oxc.rs/docs/guide/usage/linter/js-plugins.html).
- **React:** native React compiler checks include many Hooks rules. `react-hooks/config` and `react-hooks/gating` have [no native equivalent](https://oxc.rs/blog/2026-08-18-react-compiler-support.html); test `eslint-plugin-react-hooks` as an Oxlint JS plugin for these options or mark them uncovered. The Oxlint docs list React Hooks JS plugin conformance tests. `react/prop-types` has [no native support](https://github.com/oxc-project/oxc/commit/a5626951f121cf408452f1dccf9b986cc4b58a12): TypeScript props can cover typed components, but projects using runtime PropTypes need a proven Oxlint JS plugin rule or an explicit uncovered-rule note. Test `react/jsx-uses-vars` and `react/no-deprecated` against representative code rather than silently dropping them.
- **Export order:** [Oxfmt sorts imports but not exports](https://oxc.rs/docs/guide/usage/formatter/sorting.html). Test `simple-import-sort/exports` as an Oxlint JS plugin or mark export sorting uncovered. Do not replace it with core `sort-imports`.

**Decision boundary:** do not retain or run ESLint. Use Vize for Vue template linting, with a native task for template-only files. Use Oxlint and Oxfmt for shared checks, and `oxlint-tailwindcss` for consumer-owned Tailwind v4 class checks. Use proven ESLint-origin JS plugins inside Oxlint for needed TS/Node/React rules. Record any i18n, Vue-template Tailwind, CSS, or other checks that remain uncovered. This remains an audit: do not change configuration or remove packages before executable fixtures and design approval.
